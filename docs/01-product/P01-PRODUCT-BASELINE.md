## 1. 文档目的

本文把任务书中已经确认的产品定位、业务规则和范围固定下来，作为后续架构、数据模型、测试用例和框架实现的共同依据。

本文只写两类内容：

1. **已确认**：任务书明确要求，或由项目负责人直接给出的规则。
2. **推导项**：为了实现已确认规则而必须补上的工程约束，均标注“推导”或“建议”，并进入待确认清单。

本文不把建议包装成需求。所有产品规则缺口见 [P02 需求与待确认清单](P02-REQUIREMENTS-OPEN-ITEMS.md)。

## 2. 产品定义

CULINARY 是一款**专业个人烹饪档案与研发管理系统**。

它服务于一个长期使用、以 Android 手机为主要设备、经常在无网络环境下工作的专业烹饪者。它要解决的不是“去哪里找菜谱”，而是：

- 我做过什么，依据是什么；
- 一个配方由哪些物料组成，改动会影响什么；
- 某个商品对应哪个食材，库存还有多少，放在哪里；
- 这次要做多少，缺什么，该买什么；
- 几个月后回看，能否还原当时的配方与物料计算。

### 2.1 产品不是什么

| 不是 | 原因 |
|---|---|
| 普通菜谱收藏软件 | 收藏不是核心；配方结构、版本、物料关系才是 |
| 烹饪教学/课程软件 | 不提供课程、测验、社区教学 |
| 社区型菜谱分享软件 | 单用户、本地优先，不做账号与社交 |
| 通用笔记软件 | 字段与关系为烹饪研发专门设计，不是自由文本堆叠 |
| 餐厅 ERP | 不做财务、人事、桌台、供应链结算等企业资源计划 |
| 依赖 AI 才能使用的软件 | AI 不是核心功能，断网、无模型也必须完整可用 |

## 3. 目标用户与使用情境

### 3.1 用户画像

单一用户：一位需要长期积累配方、管理少量商品与库存、进行小批量制作或研发的专业烹饪者。

用户特征（推导）：

- 能理解“配方版本”“批次”“预留库存”等专业概念；
- 接受结构化录入，不追求“三秒记一条”的极简；
- 更在意数据不丢、关系正确、历史可追溯，而不是社交分享；
- 主要在厨房、储藏间、采购现场使用手机，网络不稳定；
- 会在同一台设备上使用数年，数据量逐步增长。

### 3.2 核心情境

| 情境 | 用户目标 | 关键能力 |
|---|---|---|
| 配方研发 | 记录配方结构、调整比例、保留历史 | 配方版本、组成物料、嵌套引用、循环检测 |
| 配方复用 | 把酱汁/高汤/预制件作为组件复用 | 酱汁库、菜谱库、引用与展开 |
| 制作前 | 确定做几份、需要哪些物料、缺多少 | 制作计划、配方展开、需求汇总、库存对比 |
| 采购 | 把缺口变成采购单，到货后入库 | 采购单、部分到货、批次入库 |
| 库存 | 知道每个商品有多少、在哪、何时到期 | 批次、位置、预留、流水 |
| 扫码 | 快速找到商品或录入条码 | 本地条码/二维码识别 |
| 回看 | 还原某次制作的配方与物料依据 | 计划快照、版本、变更记录 |
| 换机/恢复 | 数据可带走、可验证、可恢复 | 备份、校验、恢复、迁移 |

> **MISEBASE 修订**：上表「制作前」与「采购」两行的目标由 Inventory 内部能力承接：
> 选择菜谱/份数 → 展开汇总 → 库存比较 → 缺料清单；**不建独立制作计划/采购单**。
> 「回看」所需的旧计算结果稳定性仍由版本固定 + 计算快照保证（落地方式见 MB-D-017，仍 PROPOSED）。

## 4. 系统构成

CULINARY 由两套相互关联的体系构成，不是八个互不相干的页面。

### 4.1 A. 知识档案体系

| 库 | 回答的问题 | 关键内容 |
|---|---|---|
| 酱汁库 | 这是什么酱汁，怎么组成，怎么用，能放多久 | 酱汁身份、配方版本、组成、风味、产量、储存 |
| 食材库 | 这是什么食材，怎么选、怎么存、怎么处理 | 食材身份、别名、专业描述、默认单位、食材级换算 |
| 菜谱库 | 这道菜/高汤/预制件怎么做 | 菜谱身份、分类、配方版本、组成、步骤、产量 |

**已确认规则：核心知识库只有三个。** 高汤、基础预制物料等归属菜谱库的分类，不单独建立第四个核心知识库。

三个库的字段结构必须为专业用途分别设计，不能共用一张“通用表单”草草覆盖。

### 4.2 B. 执行管理体系（**Superseded by MB-D-002**）

> MISEBASE 处置：商品管理缩减为商品/包装/条码/食材映射；库存管理保留；制作计划移出独立模块；
> 采购管理移出，采购清单归库存。下表保留 G2 原文用于追溯，不再作为 MISEBASE 建设依据。

| 模块 | 回答的问题 | 关键内容 |
|---|---|---|
| 商品管理 | 实际买的是哪个 SKU | 商品、品牌、包装规格、条码、供应商 |
| 库存管理 | 现在有多少、在哪、被谁占用 | 批次、位置、余额、预留、流水 |
| 制作计划 | 这次做什么、做多少、缺什么 | 计划、明细、配方版本、物料需求、缺口 |
| 采购管理 | 该买什么、到了多少、何时入库 | 采购需求、采购单、明细、收货、入库批次 |

### 4.3 关联关系（已确认）

- 菜谱可以引用其他菜谱作为组成部分。
- 菜谱可以引用酱汁档案。
- 菜谱可以引用食材档案。
- 食材档案与实际商品分离：一个食材可关联多个商品。
- 库存关联实际商品，而不是只关联抽象食材。
- 制作计划加入菜谱后，按配方关系拆解物料需求，结合实际商品与库存计算缺口，形成采购需求。

## 5. 已确认的产品规则

以下规则来自任务书，属于不可擅自改变的产品约束。

### 5.1 食材与商品分离

- 食材档案描述“黄油”本身：来源、风味、挑选、储存、处理、换算。
- 商品档案描述实际采购单元：`Président 200g`、`Elle & Vire 1kg`。
- 一个食材可关联多个商品；商品必须能追溯到一个食材。
- 库存按商品与批次管理，不按抽象食材管理。
- 推荐给菜谱的“黄油 200g”在计划阶段必须先落到具体商品与批次，才能判断缺口与入库。

### 5.2 图片完全可选

适用于知识档案、商品、库存、研发记录等所有模块：

- 没有图片时，不显示图片区域。
- 只有主图时，只显示主图。
- 存在过程图时，才显示过程图区域。
- 删除全部图片后，图片区域自动隐藏。
- 不允许通过空白图片框制造虚假的内容占位。
- 图片文件缺失但档案仍存在时，档案不得因此无法打开；应记录诊断信息并按“无图”处理。

### 5.3 扫码

- 支持二维码与条形码识别。
- 本地识别优先，核心场景不依赖网络。
- 预留在线商品信息查询能力，但不得成为软件正常运行的必要条件。
- 扫码服务于商品录入、商品查询、库存操作等场景。
- 扫码失败时必须允许手工输入条码。

### 5.4 离线优先

- 主要使用设备是 Android 手机。
- 档案查看、编辑、库存操作、计划计算、采购登记、备份恢复必须在无网络时可用。
- 网络仅作为未来数据同步、在线查询等扩展能力。
- 不能因为没有网络导致核心业务不可用。

### 5.5 不允许 AI 成为核心依赖

- 本阶段不引入 AI 生成配方、AI 识别图片、AI 推荐等核心功能。
- 任何未来 AI 能力都必须是可关闭、可降级、非必要的附加能力。

## 6. 能力范围基线

优先级定义：`Must` = 首个可用版本必须；`Should` = 首个可用版本尽量；`Won't` = 本阶段明确不做。

### 6.1 知识档案

| 能力 | 优先级 | 说明 |
|---|---|---|
| 食材档案 CRUD、别名、分类、专业字段 | Must | 字段见数据字典 |
| 酱汁档案 CRUD、配方版本、组成 | Must | 酱汁本身也是配方 |
| 菜谱档案 CRUD、分类、配方版本、组成 | Must | 高汤/预制件用分类表达 |
| 配方行引用食材/酱汁/菜谱 | Must | 递归展开 |
| 循环引用检测 | Must | 保存/发布/计划确认时都要拦截 |
| 配方产量与按比例缩放 | Must | 缩放必须有单位依据 |
| 配方版本与历史 | Must | 已发布版本不可变 |
| 搜索与筛选 | Must | 名称、别名、分类、状态 |
| 图片（主图/过程图） | Should | 完全可选 |
| 变更记录 | Should | 关键档案修改可追溯 |

### 6.2 执行管理（**部分 Superseded by MB-D-002**）

> 保留：商品/包装/条码/食材映射、库存批次/位置/预留/流水、配方展开/合并/缺口、盘点/调整。
> **Superseded**：「制作计划、多菜品、独立数量」与「采购需求、采购单、部分到货」不再作为
> MISEBASE 首个可用版本的 Must；需求计算与缺料清单归 Inventory，计划/采购不作为独立模块。
> 下表保留 G2 原文，括号内为 MISEBASE 处置。

| 能力 | 优先级 | 说明 |
|---|---|---|
| 商品档案、包装规格、条码 | Must | 商品必须关联食材（MISEBASE 保留；不做供应商管理） |
| 食材—商品关联 | Must | 一对多 |
| 库存批次、位置、到期日 | Must | 批次是库存最小追溯单元 |
| 库存预留/可用 | Must | 预留与实际扣减分离 |
| 库存流水 | Must | 所有变更可追溯，禁止直接改数 |
| 制作计划、多菜品、独立数量 | ~~Must~~ **Superseded** | 日期可空；MISEBASE 不建独立计划模块 |
| 配方展开、重复物料合并、缺口 | Must | 以确认时快照为准（快照语义见 MB-D-017，仍 PROPOSED） |
| 采购需求、采购单、部分到货 | ~~Must~~ **Superseded** | 到货生成批次；MISEBASE 不做采购单/到货 |
| 采购取消、差异处理 | ~~Should~~ **Superseded** | 规则待确认，架构需支持；MISEBASE 不做采购 |
| 库存盘点/调整/报损 | Should | 必须走流水 |
| 成本/价格统计 | Won't（本阶段） | 保留价格字段，不做报表 |

### 6.3 平台与数据

| 能力 | 优先级 | 说明 |
|---|---|---|
| 本地条码/二维码扫描 | Must | 本地模型，离线可用 |
| 自动/手动备份 | Must | 校验、版本、恢复 |
| 数据导入预检查与回滚 | Must | 不允许无保护覆盖 |
| 数据迁移 | Must | 前向迁移，失败可恢复 |
| 在线商品查询 | Won't（本阶段） | 仅预留接口 |
| 云同步/账号/多设备 | Won't（本阶段） | 仅保留数据扩展缝 |
| 多用户/权限 | Won't | 单用户本地 |

## 7. 质量属性

这些是架构验收条件，不是“以后再说”的优化项。

| 属性 | 基线要求 | 验证方式 |
|---|---|---|
| 离线可用 | 无网络时全部核心流程可完成 | 飞行模式端到端测试 |
| 数据完整性 | 库存不为负；预留不超过在手；流水不可改 | 约束 + 并发测试 |
| 历史可追溯 | 已确认计划不因配方修改而改变 | 快照回放测试 |
| 可恢复 | 任意一次成功备份可验证并恢复 | 备份/恢复演练 |
| 可维护 | UI 不直接写 SQL；模块边界可检查 | 依赖规则 + 代码审查 |
| 性能 | 2 万级档案、10 万级流水下仍可操作 | 基准测试 |
| 隐私 | 默认不上传任何数据 | 网络权限审计 |
| 可用性 | 图片缺失、条码失败、单位不可换算时给出可理解结果 | 异常场景测试 |

### 7.1 建议的性能目标（推导，非已确认）

| 场景 | 目标 |
|---|---|
| 冷启动到可交互 | 中端机 ≤ 2.5 s |
| 档案列表首屏 | ≤ 300 ms |
| 名称搜索（2 万条） | ≤ 200 ms |
| 单次配方展开（≤ 200 节点） | ≤ 500 ms |
| 计划确认（含汇总/缺口） | ≤ 1.5 s |
| 单条库存写入 | ≤ 100 ms |
| 自动备份（100 MB 数据） | 后台完成，不阻塞前台 |

这些目标用于指导索引、分页和后台任务设计；若实测不达标，优先修架构，不先做“加载中”掩盖。

## 8. 成功标准（**第 3/4/5 条按 MISEBASE 范围重新解释**）

> MISEBASE 不要求独立计划/采购模块。第 3 条改为「能选择菜谱与份数，展开、合并、换算、
> 对比库存并给出缺料清单」；第 4 条的旧结果稳定性由版本固定 + 计算快照保证；
> 第 5 条改为「入库/出库/调整走批次与流水，库存非负、预留不超在手」。
> 下列原文保留，用于追溯 G2 验收口径。

首个可用版本（不要求 UI 精美）满足以下条件才算产品成立：

1. 能建立食材、酱汁、菜谱三个库，并正确表达“菜谱引用酱汁/菜谱/食材”。
2. 能对任意配方做循环检测；循环配方不能被发布或加入计划。
3. 能创建多菜品制作计划，按配方展开、合并重复物料、对比库存、给出缺口。
4. 配方修改后，已确认计划的物料需求不变；刷新计划会产生新快照并可对比。
5. 能登记采购、部分到货、入库批次；库存有批次、位置、预留、流水。
6. 能扫码或手工输入条码找到商品。
7. 无网络时以上全部可用。
8. 能生成备份、校验备份、在另一台设备恢复；损坏备份被拒绝且不破坏现有数据。
9. 数据库升级失败时能回到升级前状态并给出可操作提示。
10. 代码结构允许新增一个业务模块而不修改无关模块。

## 9. 约束与假设

### 9.1 已确认约束

- Android 手机为主要设备。
- 离线优先。
- 单用户、本地数据。
- 不依赖 AI。
- 不引入云账号、多人协作、实时同步。
- 图片可选，不得用空占位。
- 食材与商品分离。

### 9.2 推导假设（需在 P02 中跟踪）

| 假设 | 影响 | 状态 |
|---|---|---|
| 数据规模在 2 万档案、10 万流水以内 | 决定是否需要 FTS、分页、冷热分离 | 待确认 |
| 单设备使用，不做多进程 | 决定 SQLite 连接与并发模型 | 待确认 |
| 中文为主、英文为辅 | 决定搜索分词与排序 | 待确认 |
| 不做商业售卖/多租户 | 决定权限、审计、加密强度 | 待确认 |
| 价格只做记录，不做财务核算 | 决定金额精度与报表范围 | 待确认 |
| 配方按线性比例缩放，不考虑烹饪损耗 | 决定是否需要得率/损耗字段 | 待确认 |

## 10. 术语表

| 术语 | 定义 |
|---|---|
| 食材（Ingredient） | 抽象食材知识实体，如“黄油” |
| 商品（Product） | 实际采购 SKU，如“Président 黄油 200g” |
| 酱汁（Sauce） | 一种可被引用的配方型知识档案 |
| 菜谱（Recipe） | 菜品、高汤、预制件等配方型知识档案 |
| 配方版本（Formula Version） | 某次发布时不可变的组成、产量、步骤快照 |
| 组成行（Component） | 配方中的一行物料，可指向食材、酱汁或菜谱 |
| 展开（Explosion） | 按引用关系递归计算所有基础物料 |
| 物料需求（Requirement） | 展开并汇总后的食材级需求量 |
| 缺口（Shortage） | 需求量减去可用库存后的不足量 |
| 批次（Batch/Lot） | 一次入库形成、可独立追溯的库存单元 |
| 预留（Reservation） | 为计划锁定但尚未实际扣减的数量 |
| 可用库存（Available） | 在手数量减去预留数量 |
| 快照（Snapshot） | 计划确认时固化的配方、需求、缺口与计算版本 |
| 回档（Rollback） | 代码或数据恢复到先前状态；两者不是一回事 |
