# MISEBASE 范围冻结建议

**文档编号**：MB-S0-02
**版本**：`0.1.0`
**状态**：`Review`（建议稿；需项目负责人签署后才生效）
**日期**：2026-11-04
**依据**：MISEBASE 总任务书第二部分、第三部分；G2 P01；G2 决策登记册
**效力**：本文件不替代总任务书。总任务书与本文件冲突时，以总任务书为准；本文件只把总任务书转成可执行的边界。

---

## 1. 冻结目标

把 MISEBASE 的产品范围固定为**五项用户可见功能**：

1. 酱汁库 Sauces；
2. 食材库 Ingredients；
3. 菜谱库 Recipes；
4. 库存 Inventory（含自动采购清单）；
5. 扫码导入 Scan。

并明确：**设置 Settings 是工程基础设施入口，不是第六项业务功能。**

本冻结要解决三个现实问题：

- G2 的 P01 仍按「商品 / 库存 / 计划 / 采购」四个执行模块设计；
- G2 的 31 表 schema 已包含规划、采购、供应商结构；
- 历史模块 `feature:planning`、`feature:procurement` 仍存在。

---

## 2. 五项功能定义

### 2.1 酱汁库 Sauces

**目的**：保存、维护、查询酱汁配方，并可被菜谱引用。

**必须能力（任务书已明确）**：

- 名称、描述、标准产量；
- 配方原料（食材/酱汁/菜谱引用）、数量、单位；
- 制作步骤；
- 时间、温度、火候、设备参数；
- 成品状态与质量标准；
- 版本记录；
- 与其他酱汁、食材、菜谱的关联；
- 可被菜谱引用；必要时支持子配方展开。

**关键规则**：

- 已发布版本不可变；编辑产生新版本（D-006）；
- 旧版本可被旧菜谱/旧计算结果引用；
- 子配方引用必须能固定到明确版本。

**现有资产**：`sauce`、`sauce_version`、`sauce_component` 三表；无领域模型/Repository/UI。

**完成判定**：用户能创建酱汁、编辑组成与步骤、发布版本、查看历史；菜谱能引用指定版本并在展开中正确计算。

---

### 2.2 食材库 Ingredients

**目的**：统一维护食材档案，避免同一食材重复建立。

**必须能力（任务书已明确）**：

- 名称、分类、描述；
- 标准计量单位；
- 单位换算关系；
- 必要的规格信息；
- 与酱汁、菜谱的关联；
- 与扫码商品的映射关系；
- 同一种食材尽量引用统一标准记录。

**关键规则**：

- 食材是抽象知识实体，商品是实际采购 SKU（P01 已确认的分离原则仍适用）；
- 单位换算遵循 D-008：同维度按基准因子；跨维度只允许食材级显式换算；无依据拒绝并分行；
- 名称规范化 + 唯一性约束（现有部分唯一索引）。

**现有资产**：完整纵向切片（列表/新建/编辑/归档）；`unit`、`ingredient`、`ingredient_alias`、`ingredient_unit_conversion` 四表；`UnitConverter` + 13 个测试。

**完成判定**：CRUD、别名、换算、详情、图片（可选）、与菜谱/酱汁的引用关系可查看。

---

### 2.3 菜谱库 Recipes

**目的**：以结构化配方为核心，支持标准批次、SOP、成品标准、版本与子配方。

**必须能力（任务书已明确）**：

- 标准产量（批次/份数/单份重量）；
- 标准配方：食材或酱汁引用、标准数量、单位、处理说明；
- 标准 SOP：有序步骤、温度、时间、火候、设备、静置、检查点、成品判断；
- 成品标准：预期重量、质地、酱汁浓度、出品状态、产量允许误差；
- 配方版本：历史不可覆盖；修改留版本；子配方固定版本；旧版本计算结果不因新版本变化。

**关键规则**：

- 已发布版本不可变（D-006）；
- 菜谱可引用食材、酱汁、其他菜谱；循环引用必须拒绝（现有 `RecipeGraphValidator`）；
- 按目标份数缩放时，以标准产量为基准；缩放规则必须可解释、可测试；
- 旧计算结果的稳定性由「版本固定 + 计算快照/引擎版本」保证（D-007 的语义，落地方式待定，见 §6）。

**现有资产**：`recipe`、`recipe_version`、`recipe_component` 三表；`Recipe`/`RecipeVersion`/`RecipeComponent` 领域模型；`RecipeExploder`、`RequirementAggregator`、`InventoryAllocator`、`SnapshotPayloadCodec`；无 UI。

**完成判定**：列表/详情/编辑器；组成行增删改；SOP 编辑；发布版本；按份数缩放并展示物料需求；旧版本可回看。

---

### 2.4 库存 Inventory

**目的**：维护实际物料数据，并把菜谱配方转换为物料需求、库存比较与缺料清单。

**必须能力（任务书已明确）**：

- 当前库存；
- 入库、出库、库存调整；
- 库存流水；
- 计量单位；
- 配方需求计算；
- 库存扣减计算；
- 缺料数量计算；
- 自动采购清单。

**核心流程（任务书已明确）**：

1. 选择菜谱并输入制作份数；
2. 按标准批次和目标份数缩放；
3. 递归展开引用的酱汁和子配方；
4. 合并重复材料；
5. 执行单位换算；
6. 与当前库存比较；
7. 库存足够 → 不生成不必要缺料项；
8. 库存不足 → 生成缺少数量与采购清单。

**关键规则**：

- 库存变化必须走流水，禁止直接改数字（D-009）；
- 库存扣减与流水写入同一事务；
- 数量不得为负；预留不得超过在手（现有约束/触发器）；
- 单位不可换算时必须显示“无法换算”，不能猜数（D-008）；
- 采购清单是库存模块内部能力，不是独立业务模块。

**现有资产**：`inventory_batch`、`inventory_ledger`、`inventory_reservation` 三表；`InventoryAllocator`、`RequirementAggregator`；无 Repository/UI/入库出库流程。

**完成判定**：库存总览、物料详情、入库/出库/调整、流水、需求计算、扣减、缺料清单完整闭环；并发/负库存/单位异常有测试。

---

### 2.5 扫码导入 Scan

**目的**：把包装商品映射到食材档案并导入库存。

**必须能力（任务书已明确）**：

- 二维码扫描；
- 条形码扫描；
- Android 摄像头识别；
- 本地识别；
- 本地商品或食材匹配；
- 无匹配时手动创建或映射；
- 包装规格和数量确认；
- 商品映射到食材；
- 确认后导入库存。

**关键规则**：

- 本地识别，离线可用；不引入 AI 商品识别/自动补全；
- 在线商品查询不是当前必要功能；
- 相机权限拒绝时必须允许手工输入条码（现有 `BarcodeParser` 兜底）；
- 扫码结果必须经过“商品/食材匹配 + 包装规格 + 数量”确认，不能一扫直接入库；
- 导入库存必须生成流水/批次，不能直接改余额。

**现有资产**：`BarcodeScanner` 端口、`BarcodeParser`、`BarcodeFormats`、`MlKitBarcodeDecoder`、`CameraBarcodeScanner`、权限三态；**无扫码 UI、无设备验证**。

**完成判定**：真实 Android 设备完成“扫码 → 匹配/创建 → 包装规格/数量 → 确认入库 → 流水可查”全流程；权限拒绝/无匹配/重复条码有明确处理。

## 3. 明确排除（任务书第三部分）

以下**不得**作为 MISEBASE 功能加入：

- AI 助手、AI 生成配方、AI 商品识别、AI 自动补全；
- 学习系统、学习计划、课程、考试、测验；
- 独立技术知识库、独立经典菜肴知识库；
- 独立实验室/实验管理；
- 餐厅 ERP、多门店、角色权限、员工管理、多人协作、云账户、社区、社交分享；
- 复杂供应商管理、自动采购下单、供应链平台；
- 独立生产计划平台、独立复杂规划体验。

**允许的工程基础设施**：数据库、迁移、备份恢复、事务、并发控制、日志、崩溃恢复、图片存储、版本管理、测试、构建、Git、依赖检查、离线运行。

## 4. 与 P01 的取代关系（需负责人签字）

P01 的 §4.2「执行管理体系」定义四个模块，与本冻结冲突。建议处理：

| P01 内容 | 建议处置 |
|---|---|
| 商品管理（商品、品牌、包装、条码、供应商） | **缩减**为「商品/包装/条码/食材映射」，仅服务扫码与库存；供应商管理移出 |
| 库存管理（批次、位置、预留、流水） | **保留**，作为五项功能之一 |
| 制作计划（计划、明细、快照、需求、缺口） | **移出独立模块**；需求/缺口能力归入库存计算；快照语义按下节处理 |
| 采购管理（采购需求、采购单、部分到货、入库） | **移出**；只保留库存内的「缺料清单」；不做采购单/到货/供应商 |
| P01 §6.2 中「采购单、部分到货 Must」 | **Superseded**，不再作为 MISEBASE 首个可用版本要求 |

建议在 P01 顶部加一条 `Superseded by MB-S0-02 / 总任务书` 的说明，但**不删除原文**，保留历史可追溯。

## 5. 范围边界中的灰区

以下问题任务书没有给出唯一答案，必须在阶段 0 冻结，否则实现会各写一套。

| # | 灰区 | 建议默认值 | 需确认 |
|---|---|---|---|
| G-01 | 库存是否保留「批次 + 位置 + 预留」 | **保留**（D-009 已接受；可先做简化 UI，不取消数据能力） | 项目负责人 |
| G-02 | 采购清单是否落库 | **不落采购单表**；按需计算并展示，可导出文本；`purchase_order*` 休眠 | 项目负责人 |
| G-03 | 制作计划/计划快照是否保留 | **不保留独立计划模块**；如需要历史稳定，用「计算记录 + 菜谱版本 + 引擎版本」实现快照语义 | 项目负责人/架构 |
| G-04 | 子配方引用是否发布时固定版本 | **是**：草稿可指向当前版本，发布时解析并写入明确版本 ID；已发布版本不再跟随 | 项目负责人/架构 |
| G-05 | 缩放是否线性 | **线性**（按标准产量比例）；烹饪损耗/得率本阶段不做 | 项目负责人 |
| G-06 | 可选配料（D-018）是否计入缺料 | **可标记 optional；默认不计入缺口，但在详情中显示** | 项目负责人 |
| G-07 | 库存扣减是“预览”还是“确认即扣” | **两步**：先计算预览，用户确认后写流水；取消不产生副作用 | 项目负责人 |
| G-08 | 扫码导入的单位 | 以商品 `stock_unit` 入库；包装规格换算到库存单位；无法换算则拒绝并提示 | 项目负责人 |
| G-09 | 商品是否必须有供应商 | **否**；供应商字段可空/休眠；不做供应商管理 UI | 项目负责人 |
| G-10 | 图片是否首版必须 | **可选**；缺失不阻塞档案读取（P01/D-015 已确认） | 项目负责人 |

> 这些默认值只是建议，**不是已确认需求**。未签字前，开发不得把它们当作最终规则。

## 6. 五项功能的验收口径

| 功能 | 最低验收 |
|---|---|
| 酱汁 | 创建/编辑/发布/历史；被菜谱引用；子配方展开正确；版本不可变测试 |
| 食材 | CRUD/别名/换算/详情；被菜谱/酱汁引用；重复名称冲突提示 |
| 菜谱 | 结构化配方 + SOP + 成品标准；按份数缩放；循环检测；旧版本结果稳定 |
| 库存 | 入库/出库/调整/流水；需求展开/合并/换算/比较；缺料清单；并发/负库存测试 |
| 扫码 | 真机扫码（QR + Barcode）；无匹配手工创建/映射；包装规格确认；导入流水 |
| 设置 | 备份/恢复/诊断可用；恢复失败不破坏现有数据 |

---

## 7. 范围变更控制

1. 任何新增用户可见功能，必须先新增决策并更新本文件；
2. 任何“顺手做”的采购/计划/供应商能力，一律拒绝；
3. 历史代码中的超范围能力，先审计、标记、停用，不直接删除；
4. 每次阶段验收，对照本文件检查“是否多做了”与“是否少做了”。
