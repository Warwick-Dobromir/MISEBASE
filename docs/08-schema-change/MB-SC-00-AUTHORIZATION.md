## 2. 执行顺序（强制）

Schema 变更任务必须按以下顺序推进，任一步未通过不得进入下一步：

1. **任务书**：独立任务书，明确范围、验收条件与禁止项；
2. **迁移方案**：目标结构、向前/向后兼容、数据回填、索引与触发器影响；
3. **结构审查**：与 A05/A06、11 张休眠表边界、备份格式核对；
4. **备份恢复方案**：迁移前备份、失败恢复、WAL/写屏障边界（不得修改既有备份行为，
   除非另有签收的任务书明确授权）；
5. **实施**：仅在迁移任务分支/提交内修改 Schema、Entity、DAO 与迁移；
6. **自动化测试**：JVM + Room 迁移测试、结构断言、回填数据验证；
7. **备份恢复验证**：迁移前后备份可恢复，恢复后结构与数据一致；
8. **迁移回滚验证**：按 MB-S1-05 的迁移/备份/回滚清单验证失败路径；
9. **报告审查签收**：独立报告 + 负责人审查；签收前 Stage 3 不得启动。

## 3. 工程边界（强制）

1. **Schema v1 在迁移完成前仍是有效基线**；不得宣称 v2 已生效。
2. 不得直接改**正式数据库**或**迁移历史**；不得删除、重建或绕过既有迁移记录。
3. 不得修改其他已签收决策（含 MB-D-013/014/015/016/017 的业务语义）。
4. Schema 变更必须**独立审查与验收**，不得混入功能开发提交。
5. 计算记录的**实际业务功能**仍按 Stage 4 计划实施；本次只做持久化地基，
   **不扩大 Stage 3 范围**。
6. **Stage 3 不得在 Schema 变更签收前启动**；起点标签只表示"可启动的前提位置"，
   不构成启动授权。
7. 11 张休眠表仍不得删除、迁移、结构性改造或在业务代码中引用。
8. 技术栈、模块集、包名不变；不引入新数据库或并行持久化体系。
