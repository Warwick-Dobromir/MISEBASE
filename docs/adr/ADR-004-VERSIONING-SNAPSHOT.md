# ADR-004：不可变配方版本 + 计划快照

**状态**：Proposed
**版本**：`0.1.0`
**日期**：2026-11-04
**决策者**：首席架构师 / 项目负责人
**关联**：D-006、D-007、A04、A06、A07

## 背景

菜谱/酱汁会持续修改；制作计划确认后，历史物料需求不能因后续修改而改变。只保存 `recipe_id` 会跟随最新版本漂移。

## 决策

1. 菜谱/酱汁有身份表 + 不可变版本表。
2. 已发布版本只读；修改 = 复制为新草稿，发布新版本。
3. 计划项固定 `recipe_version_id`。
4. 计划确认时生成不可变快照（完整展开树 + 需求 + 缺口 + 引擎版本 + hash）。
5. 刷新计划生成新快照，旧快照保留。

## 理由

- 版本解决“配方自身如何演进”。
- 快照解决“历史计划如何不被后续修改影响”。
- 两者缺一不可。
- 支持审计、差异对比、旧计划回放。

## 后果

- 发布动作增加一步；用户需要理解“草稿/已发布”。
- 存储增加；快照 JSON 可能较大。
- 旧快照必须按旧引擎版本解释，不能重算。
- 已发布版本纠错需要数据修复流程，不能直接改。

## 替代方案

- 只存 recipe_id：历史漂移，不可接受。
- 只存快照：无法解释配方版本演进。
- 事件溯源：过重，不适合个人软件。

## 复审条件

- 用户明确不需要历史回放（与已确认需求冲突）；
- 快照存储/性能成为瓶颈，需要归档策略。
